QAOA Space Pathfinding Primer

Everything you need to follow the project on finding spacecraft trajectories that navigate through asteroids and debris, explained for a software engineer who has never touched quantum computing or path planning. Part 1 builds the concepts from zero. Part 2 surveys what already exists. Part 3 says what that means for our plan.

The short version

  • Our problem has two halves: find a fuel-efficient trajectory for a spacecraft, and make it navigate safely around moving asteroids and debris. We model both as a shortest path over a graph of (position, velocity, time) states, the home turf of A*.
  • People have already run QAOA on small shortest-path and grid path-planning problems, on small routing problems (TSP), and quantum annealing on space problems (trajectories, debris removal). The consistent finding: at sizes today's machines and simulators can handle, good classical methods win.
  • So the "threshold where quantum beats classical" will very likely not appear in our experiments. That is still a publishable, useful result if we measure it carefully. What's missing in the literature is an open, reproducible, gate-based QAOA benchmark that combines trajectory planning with hazard avoidance (momentum, fuel costs, moving asteroids and debris). That is where we can add something.

Part 1 · Concept 1
Path planning is an optimization problem

"Path planning" covers two different questions, and it helps to keep them apart:

  • Point-to-point: how do I get from A to B while avoiding obstacles? (Google Maps directions, a robot crossing a room.)
  • Ordering, or routing: I must visit many places. In what order should I visit them so the total cost is lowest? (A delivery driver's day, a spacecraft touring asteroids.)

Our project is the first kind, with physics. A spacecraft must reach a goal through a field of asteroids and debris. We want a trajectory (its route through space over time) that uses the least fuel and never collides. Fuel is measured as Δv, "delta-v", the change in velocity the engine must deliver.

Space differs from a road map in one key way: momentum. A spacecraft keeps drifting at its current velocity for free, and every change of speed or direction needs a burn that costs Δv. So we plan over states, not just positions: a state is (position, velocity) at a moment in time. Each step the spacecraft either coasts or fires a small burn, which decides the next state. States that overlap an asteroid or debris at that moment are removed. This graph of states is called a state lattice.

SDE analogy

It is a state machine where each transition has a cost. Nodes are (position, velocity, time), edges are "coast" or "burn", and some nodes are forbidden because a rock is there at that moment. Find the cheapest run from the start state to a goal state. The number of possible runs explodes, so you need a clever search, not enumeration.

"Optimization" just means: define a cost function (total Δv), define the constraints (start at the start, end at the goal, obey momentum, never touch a hazard), and find the input that minimizes cost while respecting constraints. Every solver in this project, classical or quantum, is a different strategy for that same search.

Part 1 · Concept 2
Classical solvers

These are the baselines the quantum approach has to beat.

Dijkstra (exact)

Start at the start node and expand outward, always taking the cheapest unexplored node next from a priority queue. When you pop the goal, you have the guaranteed cheapest path. Runs in O(E log V), so it handles grids with millions of cells easily. It is our ground truth for scoring every other method.

A* search (the main baseline)

A* is Dijkstra plus a heuristic that guesses the remaining cost, such as the straight-line distance to the goal. Nodes are prioritized by "cost so far + estimated cost to goal", so it explores toward the goal first and skips most of the grid. If the guess never overestimates, the answer is still optimal. It is the standard tool for exactly our problem: games, robots, and rovers all use it. Run over a state lattice it's called kinodynamic planning.

Real missions also use continuous trajectory optimization: calculus-based solvers that shape a smooth path (for example direct collocation). We stick to a discrete lattice so that classical and quantum solvers attack exactly the same problem.

SDE analogy

Dijkstra is a BFS where the queue is a min-heap on cost. A* is the same code with one extra term in the heap key. That tiny change is why it's so fast in practice.

Integer Linear Programming (ILP)

You write the problem declaratively as variables, linear constraints, and a linear objective, then hand it to a solver (OR-Tools, Gurobi, HiGHS, PuLP). The solver uses branch-and-bound: it splits the search space, computes cheap lower bounds, and prunes whole branches that cannot beat the best answer found so far.

SDE analogy

ILP is to optimization what SQL is to data. You describe what you want, and a decades-tuned engine figures out how. Modern solvers handle problems with millions of variables.

Simulated annealing (heuristic)

Start with some path, repeatedly make a small change (reroute one section), and keep it if it's better. Sometimes keep a worse one too, with a probability that shrinks over time (the "temperature" cools). Early on it explores; late it settles. It's hill climbing that can escape local minima. It is fast and simple. Crucially, it can take the exact same QUBO as QAOA (next section), which makes it the fairest head-to-head comparison.

Part 1 · Concept 3
QUBO: the format quantum optimizers accept

Quantum optimizers don't take "a list of asteroids and a cost matrix". They take one specific shape of problem called QUBO, short for Quadratic Unconstrained Binary Optimization:

  • Binary: every decision is a bit, x = 0 or 1.
  • Quadratic: the cost is a sum of terms involving at most two bits at a time: cost(x) = Σ Qij · xi · xj.
  • Unconstrained: there are no separate rules. Any rule must be baked into the cost.

For a path, the usual trick (in the style of Lucas 2014) uses one bit per edge of the grid: x[e] = 1 means "edge e is part of the path". Rules like "whatever enters a cell must leave it" become penalty terms: a big number added to the cost whenever a rule is broken. Blocked cells are simply removed from the graph, so their edges never become bits.

The example below is the warm-up: a static path with no momentum. The full trajectory version uses one bit per (time step, state), "the spacecraft is in this state at this time", with a pairwise term for the Δv of each allowed transition and a penalty for impossible ones. Same idea, more bits.

# 3x3 grid, start S top-left, goal G bottom-right, one debris cell X
#   S - . - .
#   |   |   |
#   . - X - .      edges touching X are removed
#   |   |   |
#   . - . - G
# bit x[e] = 1 means "the path uses edge e"

cost(x) =  Σ_e  dv[e] * x[e]                             # fuel for each step
        + P * (1 - Σ_{e out of S} x[e])²                 # leave the start once
        + P * (1 - Σ_{e into G}  x[e])²                  # arrive at the goal once
        + P * Σ_{other cells v} (Σ_in x[e] - Σ_out x[e])²   # no dead ends
# P is "big enough" that breaking a rule never pays off
SDE analogy

Penalty terms are like replacing hard validation (throw on bad input) with a huge score deduction. The optimizer is allowed to propose invalid answers; they just score so badly that it learns to avoid them. The catch: it still proposes them sometimes, so we must check and count how often.

Cost of this encoding: one bit per usable edge. A 4×4 grid already has 24 edges. That number becomes the number of qubits, and it grows fast.

Part 1 · Concept 4
Qubits and quantum circuits

A normal bit is 0 or 1. A qubit holds a pair of numbers called amplitudes, one for 0 and one for 1. When you measure it, you get 0 or 1 at random, with probabilities given by those amplitudes squared, and the qubit then stays at whatever you saw.

With n qubits, the state holds one amplitude for every possible n-bit string: 2ⁿ numbers. That's where both the excitement and the misunderstanding come from.

SDE analogy

Picture a register of n qubits as a probability distribution over all 2ⁿ bitstrings that you can reshape with operations, but can only sample from, one bitstring per run. You never get to read the whole table. The art is to reshape the distribution so the good answers come out often. It is not "tries every answer in parallel and returns the best".

  • Gates are the operations. A gate acts on one or two qubits and rotates their amplitudes. Like instructions in assembly.
  • Circuit is a sequence of gates, the program. You run it many times (called shots, e.g. 1,024) and get a histogram of measured bitstrings.
  • Superposition is simply a state with nonzero amplitude on many bitstrings at once.
  • Entanglement means the qubits' outcomes are correlated in a way that can't be described one qubit at a time, e.g. "these two always come out equal".
  • Interference is the real trick. Amplitudes can be negative (in fact complex), so paths leading to a bad answer can cancel out while paths to a good answer add up. Algorithms are designed around this.

In Python, Qiskit lets you build a circuit like any other object, then run it on a simulator or on IBM hardware.

Part 1 · Concept 5
QAOA, the algorithm we'll use

The Quantum Approximate Optimization Algorithm (Farhi, Goldstone and Gutmann, 2014) takes a QUBO and builds a circuit whose output samples are biased toward low-cost bitstrings. It alternates two kinds of layer:

  • Cost layer, angle γ: nudges each bitstring's amplitude by an amount that depends on its QUBO cost. Good and bad answers get "marked" differently.
  • Mixer layer, angle β: lets amplitude flow between neighboring bitstrings, so the state can move toward the marked good ones.

Repeat the pair p times (the depth). Bigger p can give better answers but a longer circuit, which hurts on noisy hardware.

SDE analogy

It's hyperparameter tuning. The circuit is a model with 2p knobs, the loss is the average QUBO cost of its samples, and a classical optimizer turns the knobs. At the end you take the best valid bitstring you ever sampled and decode it back into a path.

Known practical problems for path and routing QUBOs: many samples break the rules (broken or looping paths), the angle search gets stuck in flat regions as problems grow, and the qubit count outgrows simulators quickly. Variants that help: warm-starting from a classical solution, pruning edges that can't be on a good path before building the circuit, and constraint-preserving mixers.

Part 1 · Concept 6
Simulators vs real quantum hardware

A statevector simulator is an ordinary program that stores all 2ⁿ amplitudes in RAM (16 bytes each) and applies gates as matrix math. It is exact and noise-free, but memory doubles with every qubit.

Obstacles remove edges and classical pruning removes more, so real counts are a bit lower; a space-time grid multiplies them by the number of time steps. For comparison, A* solves a 1000×1000 grid in well under a second. Other simulators (tensor-network or "matrix product state") can go further for shallow circuits, but they have their own limits.

Real hardware (e.g. IBM's machines, free tier available) has more than 100 qubits, but they are noisy: every gate has a small error rate, qubits lose their state within microseconds, and not every qubit can talk to every other, so extra "swap" gates get inserted. Deep QAOA circuits on 25+ qubits come out mostly as noise today. You also wait in a queue and pay per shot beyond the free allowance.

SDE analogy

The simulator is your local dev environment: perfect, deterministic-ish, but it can't scale. Hardware is production on flaky infrastructure with a cold-start queue. Our experiments will mostly live on the simulator, with maybe one small hardware run to show the noise effect.

Part 1 · Concept 7
What "quantum advantage" honestly means today

People use the phrase for three very different claims:

  • Provable advantage: a mathematical proof that a quantum algorithm needs fewer steps than any classical one (e.g. Shor's factoring). There is no such proof for QAOA on path planning.
  • Empirical scaling advantage: as the problem grows, the quantum method's runtime grows more slowly than the best known classical method's. The strongest QAOA evidence is Shaydulin et al. (Science Advances, 2024): better scaling than branch-and-bound on the LABS problem, a problem chosen because it is hard for classical solvers. It used noiseless simulation up to 40 qubits plus small runs on trapped-ion hardware.
  • Practical advantage: a real task solved faster, cheaper, or better on real hardware than the best classical approach. For path planning, routing and scheduling, this has not been demonstrated.

There are also theoretical warnings. Bravyi et al. (PRL, 2020) showed that low-depth QAOA provably underperforms a classical algorithm on some problem families. And a 2026 head-to-head on the related TSP routing problem (Quantitative Framework, PEARC '26) found simulated QAOA handled at most 7 cities and was beaten by simulated annealing on both quality and scalability.

What this means for us

Our honest expectation is that QAOA will not beat good classical methods at any size we can simulate. The valuable research output is the careful measurement: how path quality, valid-path rate, and cost scale with field size, obstacle density and depth p, and how far the gap is. A clean, reproducible "no, and here's exactly why" is a good paper and a strong portfolio piece.

Classical state of the art for navigating hazards

Classical path planning is mature. A* and its variants (D* Lite for replanning when obstacles move) and sampling planners like RRT* run on real robots and rovers today, and spacecraft collision avoidance is an established field. Multi-asteroid mission design is also a competitive sport: ESA's Global Trajectory Optimisation Competition publishes realistic asteroid data we can borrow for test scenarios.

Where this project can still add something

  • Quantum path-planning papers use toy grids with static obstacles and no momentum. Quantum trajectory papers optimize fuel but ignore obstacles. We found no work that combines trajectory planning with hazard avoidance.
  • Space papers use D-Wave quantum annealing, not gate-based QAOA.
  • Most papers don't publish runnable code. A clean, reproducible benchmark against A*, Dijkstra and simulated annealing, with a visualizer, is itself a contribution.
  • Comparing QAOA variants (standard vs warm-start vs classical pruning) on this problem is a small but real research question.

Part 3
Should the plan change?

The four-thread structure is sound. I'd keep it and adjust five things:

1
Model trajectory and navigation together. A state lattice of (position, velocity, time): coasting is free, burns cost Δv, and states that hit an asteroid or debris are removed. Start with a static grid path as a warm-up.
2
Reframe the research question. Instead of "at what size does quantum win", ask "how do QAOA's trajectory quality, valid-trajectory rate, and cost scale with problem size and depth, and how big is the gap to classical?" The answer is likely "no crossover in reach", and that's fine.
3
Keep A* and Dijkstra (over the state lattice) as the main baselines, and add simulated annealing on the exact same QUBO for an apples-to-apples comparison.
4
Keep QAOA scenarios tiny (a few time steps on a small grid, or a 3×3 to 4×4 static path, on the simulator), sweep depth p = 1 to 5, and try one improved variant (warm start or edge pruning). One small run on IBM hardware is a nice stretch goal.
5
Add one realistic scenario built from real asteroid or debris positions scaled down to a small grid, so the project is clearly about space.
